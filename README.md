# attendance-merge：考勤补传归并库

多个识别设备为同一员工重复产生打卡记录，断联设备恢复后还会补传很早
以前的数据。本库把同一人员的全部设备记录合并，按统一规则计算每条记录
当前是否有效，结果与上传顺序、批次划分及重传次数无关。

数据保存在调用方指定的 SQLite 文件中，只提供两类操作：批量补传、
按人员查询有效打卡。纯 Python 标准库实现，无第三方依赖。

## 有效性规则

将某人的全部记录按事件时间升序、同毫秒按事件标识 ASCII 字典序排列：
第一条有效；之后只有距离上一条**有效**记录至少 600000 毫秒（10 分钟）
才有效，否则被抑制。被抑制记录不延长抑制窗口；恰好相差 600000 毫秒
时有效。补传较早记录可能使原有效记录被抑制、原被抑制记录重新有效，
库内会沿时间轴增量重算并落库，等价于对全部唯一事件重算的结果。

## 使用

```python
from attendance_merge import AttendanceStore, Event

# 数据保存在调用方指定的 SQLite 文件中
with AttendanceStore("/path/to/attendance.db") as store:
    # 批量补传（可乱序、可含多个人员、可重复重放，幂等）
    store.ingest([
        Event(event_id="devA-0001", person_id="emp-01", ts_ms=1_696_000_000_000),
        Event(event_id="devB-0042", person_id="emp-01", ts_ms=1_696_000_300_000),
    ])

    # 查询 [start_ms, end_ms) 内的有效记录，按 (ts_ms, event_id) 升序
    valid = store.query_valid("emp-01", 1_695_000_000_000, 1_697_000_000_000)
    for ev in valid:
        print(ev.event_id, ev.ts_ms)
```

- `Event(event_id, person_id, ts_ms)`：`event_id` 为非空 ASCII 且全局唯一，
  `ts_ms` 为上游校准后的 UTC 毫秒。同一 `event_id` 重复补传内容必须一致。
- `ingest(batch) -> int`：返回本次新入库的唯一事件数；重放返回 0。
  整个批次（含增量重算）在单个事务中完成。
- `query_valid(person_id, start_ms, end_ms) -> list[Event]`：左闭右开区间，
  区间只是对完整有效记录集的裁剪，不从区间起点重算抑制窗口。
- 关闭后重新打开同一文件，已补传数据与查询结果保持一致。

## 测试与基准

```bash
python3 -m unittest discover -s tests -v   # 正确性测试
python3 bench.py                           # 规模场景耗时基准
```

正确性覆盖：连锁变化（先收 2/11/20/29/38 分钟再补 0 分钟，有效记录由
2/20/38 变为 0/11/29，且长序列同类变化一直修正到历史末尾）、同毫秒
事件、599999/600000 毫秒边界、随机乱序/分批/重复重放与独立参考实现
逐条一致、查询区间仅裁剪不重算、重开文件结果不变、重放幂等。

## 实测耗时（本机，Python 3.14）

| 场景 | 规模 | 耗时 |
| --- | --- | --- |
| 初始导入（不计入考核） | 120 万条 | 约 4 秒 |
| 单事件末尾补传 + 末尾 1 小时查询 | 连续 1000 轮 | 约 0.06 秒（要求 ≤ 15 秒） |
| 长链变化：头部补 1 条 | 翻转 20 万条历史记录 | 约 0.5 秒 |
| 全量独立重算校验 | 120 万条 | 约 1 秒，0 处不一致 |

实现要点：单人记录以 `(person_id, ts_ms, event_id)` 聚簇主键存储，
补传只从该人受影响起点增量重算，一旦新旧有效性收敛即停止扫描，
因此只影响末尾少量记录的补传开销与受影响记录数成正比，与历史总量无关。
