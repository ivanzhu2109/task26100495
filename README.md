# 考勤补传归并库（attendance_merge）

用 Python + SQLite 实现的考勤补传归并库。多个识别设备对同一员工反复产生
打卡记录、断联设备恢复后补传历史数据时，本库保证考勤结果只取决于已收到
的唯一事件集合，与上传顺序、批次划分、重传次数无关。

## 业务规则

- 每条记录含全局唯一 ASCII 事件标识、人员标识、校准后的 UTC 毫秒时间。
- 同一人员的全部记录按 `(事件时间, 事件标识字典序)` 升序排列：第一条有效；
  之后距上一条有效记录不足 600000 毫秒（10 分钟）的被抑制，恰好相差
  600000 毫秒的有效；被抑制记录不推进抑制窗口。
- 补传较早记录可能引发连锁修正（原有效变抑制、原抑制变有效），本库按
  增量方式把修正传播到历史末尾，不在固定回看范围处停止。
- 查询区间为左闭右开，只是对完整有效记录集的裁剪，不从区间起点重算窗口。

## 使用说明

```python
from attendance_merge import AttendanceStore, PunchEvent

# 数据保存在调用方指定的 SQLite 文件中
with AttendanceStore("attendance.db").open() as store:
    # 批量补传（可乱序、可跨人员、可重复重放；返回实际新增的唯一事件数）
    store.ingest_batch([
        PunchEvent(event_id="evt-0001", person_id="emp-42", ts_ms=1_700_000_000_000),
        PunchEvent(event_id="evt-0002", person_id="emp-42", ts_ms=1_700_000_600_000),
    ])

    # 查询 [start_ms, end_ms) 内的有效打卡，按 (ts_ms, event_id) 升序
    for punch in store.query_valid("emp-42", 1_700_000_000_000, 1_700_100_000_000):
        print(punch.event_id, punch.ts_ms)
```

仅两类操作：`ingest_batch`（批量补传）与 `query_valid`（按人员查询有效
打卡）。正常 `close()` 后重新打开，数据与查询结果保留。

## 实现要点

- 单表 `events(person_id, ts_ms, event_id, valid)`，主键即人员内排序；
  `event_id` 唯一索引保证重传幂等（`INSERT OR IGNORE`）。
- 每批补传在单个事务内完成：批量入库后，按人员从本批最早新增点开始
  正向重算有效性，重算到“本应有效且已标记有效”的记录且越过本批全部
  新增点时提前停止——末尾追加场景每次补传为 O(1)。
- 重算与查询均走索引范围扫描（行值比较 `(ts_ms, event_id) >= (?, ?)`），
  不随人员历史总量退化。

## 测试与性能

```bash
python3 -m pytest tests -q   # 13 个正确性测试
python3 benchmark.py         # 规模场景性能基准
```

正确性覆盖：验收连锁例（2,11,20,29,38 → 补 0 → 0,11,29）、5000 条长链
全程修正、同毫秒字典序、599999/600000 边界、随机乱序分批重复重放与独立
参考实现逐条比对、区间裁剪、关闭重开持久化。

实测耗时（本机，单人 100 万条历史）：

- 初始导入 1,000,000 条：约 7 秒（不计入预算）
- 连续 1000 次单事件末尾补传 + 每次末尾 1 小时查询：约 0.06 秒
  （预算 15 秒）
